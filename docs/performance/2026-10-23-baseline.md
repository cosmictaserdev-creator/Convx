# Release startup and scroll baseline

Measured on the user's Galaxy M34 (SM-M346B), installed non-debuggable Convx
2.0.5 (versionCode 20005), 1080 x 2340, active display rate 120 Hz.
One logical display; no Android Studio screen sharing. Thermal status was 0
(no throttling) at the subsequent conditions check. App data was preserved.

## Measurements

| Measurement | Result |
| --- | --- |
| Cold launch, launcher alias to MainActivity, `am start -S -W` | 742 / 788 / 847 ms |
| Median cold launch | 788 ms |
| Return from Home, one sample | 218 ms `WaitTime`; Android reported launch state UNKNOWN |
| Frames rendered in manual rapid-scroll capture | 1,419 |
| Deadline misses (`gfxinfo`) | 913 (64.34%) |
| Frame latency p50 / p90 / p95 / p99 (`gfxinfo`) | 34 / 65 / 85 / 150 ms |
| GPU p50 / p90 / p95 / p99 (`gfxinfo`) | 6 / 10 / 13 / 23 ms |

The 120 Hz frame budget is 8.33 ms. Latency percentiles are **not presented FPS**;
the data does not establish an average or sustained frame rate. Initial display
does not measure loaded feed readiness. The return-from-Home `WaitTime` is not
a reliable hot-start TTID measurement.

The user flung Home up and down manually. Frame counters were reset before the
signal to scroll. The capture includes settling and cannot be reproduced as an
identical gesture sequence. Results establish a problem, not an A/B improvement.

## Trace findings

The completed 40-second Perfetto recording is 33,496,088 bytes. Its retained app
slice samples cover fewer frames than the cumulative gfxinfo counters, so the
two populations must not be conflated. The process name was absent from the
process table; analysis used measured PID 18283 and RenderThread TID 18322.
No nonzero error-severity trace stats were reported by trace_processor.

| Slice | Samples | Mean | Maximum |
| --- | --- | --- | --- |
| Main traversal | 455 | 11.65 ms | 47.96 ms |
| Main postAndWait | 455 | 8.52 ms | 41.91 ms |
| Main Record View draw | 455 | 2.93 ms | 46.74 ms |
| Main animation | 460 | 5.33 ms | 59.79 ms |
| RenderThread flush commands | 452 | 6.52 ms | 25.84 ms |
| RenderThread flush layers | 449 | 4.98 ms | 36.35 ms |

Slices can be nested or overlap; do not sum these values. Main waits on rendering
for much of traversal. Rendering submission and layer processing deserve priority
over assuming the entire problem is Compose recomposition or network loading.
This trace does not identify individual composables or prove that a particular
blur, shadow, or shader accounts for a specific stall.

## Changes in this pass

- Settings initialization, including proxy setup and notification channel IPC,
  runs on IO instead of the application scope's Main dispatcher.
- Native engine prewarming and the existing opt-in Demucs download check start
  once per process after MainActivity's first draw and an idle queue turn.
  Authentication seeds, preference migrations and crash setup remain ordered as before.
- Coil disk-cache construction is lazy rather than eager in the image-loader builder.
- Blur, mesh and palette CPU processing share a two-worker dispatcher. Requests
  for matching cached treatments coalesce under bounded locks and recheck the cache.
  Work remains owned by its caller; cancellation releases the lock for later requests.
- Artwork tint effects propagate cancellation and publish an existing tint if
  another card populated the cache after this card's initial composition.

No geometry, colors, blur radii, decode sizes, quality settings, shader parameters,
animation curves or animation durations were changed. Rendering equivalence has
not yet been verified with screenshots from a rebuilt release.

## Remaining validation and architecture work

1. Compile the workspace and run ArtworkProcessingTest (coalescing, cancellation,
   and retry after unavailable images). The first attempt was blocked by concurrent
   updater compilation errors, not by the performance files.
2. Build an optimized release, compare screenshots with the installed build, and
   repeat the same startup and rapid-scroll journey. Do not use a debug build to
   claim a performance improvement. This pass does not establish 120 FPS.
3. Capture FrameTimeline with explicit `atrace_apps: com.convx.music`, a larger
   buffer and bounded gesture windows. Inspect the long layer flushes and identify
   exact glass/pool/sampler invalidations before changing the rendering pipeline.
4. Treat any duplicate layer elimination as a pixel-equivalence change: keep live
   backdrop movement, masks, refraction, shadows and transitions intact. Reusing
   stale captures or reducing blur resolution would violate the visual constraint.
5. Add meaningful `reportFullyDrawn` readiness (content, empty or error state) and
   release Macrobenchmarks/Baseline Profiles for Home, Library and long playlists.
   Cold startup alone does not describe how soon the app is useful.
